# Phase 2 — Seed/reset, test basis and management

[Previous phase](01-windows-setup.md) · [Phase list](01-windows-setup.md#phase-files) · [Next phase](03-static-analysis-and-unit-tests.md)

Tawassul owns the shared fixtures and environment handoff. Member 2 verifies that the fixtures support API readbacks and generated inputs. Member 3 verifies that they support the browser roles, accessibility checks, and comparable performance runs. The team shares test management. [Orders scope](01-windows-setup.md#selected-module-and-scope)

**Evidence.** Reproducible seed and reset commands, `sqe/test-basis.md`, scope and requirements traceability matrix (RTM), test plan, and a 5 × 5 risk matrix. The exit checks are equivalent records after two resets, W1 and W2 demonstrated on the same order, and frozen release criteria.

1. Run the Django fixture reset in native Windows PowerShell. The disposable SQLite file is under local/sqe/windows. Verify it with the two-reset procedure and use equivalent database settings for local and CI functional runs. [Commands and evidence](../../sqe/handoff.md#reset-and-verify-the-fixtures)
2. Seed a synthetic organizer and event, a EUR 20.00 item, quotas, and named pending, expired-with-quota, expired-without-quota, paid, canceled, and positionless scenarios. Create manager and viewer accounts and scoped API tokens. Stabilize clock, currency, time zone, and notifications. Check browser and API behavior separately, then run W1 → W2 against the same order code. Record fixture IDs or aliases, expected writes and observed results.
3. Validate the PAY, CAN and BR IDs against the pinned source and runtime. Record the API handlers, UI-specific validation and shared business-rule callables, with reachable branches and reasons for exclusions. Model pending, expired, paid, canceled, and fee-only outcomes. List all in-scope allowed transitions, at least one rejected action per state, and the excluded transitions. Link requirements, rules, risks, tests, results, and evidence in the RTM.
4. Record scope, risk-based depth, owners, environment, test data, schedule, and entry, exit, suspension and resumption criteria. Estimate each area optimistically, most likely, and pessimistically. Assess at least eight product risks and two project risks. Score likelihood and impact from 1–5, plot the 5 × 5 matrix, and map risks to techniques and test depth. Freeze at least three measurable release criteria, with at least two linked to the highest risks. Candidate criteria are zero duplicate writes in high-risk orders cases, zero unauthorized writes across the four role checks, and passing the predetermined order-detail load limits.
5. Keep a weekly plan-versus-actual report with control actions. Track GQM requirements coverage, defect density with a KLOC denominator, and reopen rate with its denominator. Log defects in GitHub Issues as they are found, with severity, priority, status and triage decision. Record the input files and commands needed for Phase 3 in the handoff.
6. Add the start, seed and reset commands, fixture aliases, locale, role setup, and API readback instructions to `sqe/handoff.md`. Keep credentials in local configuration. Confirm the fixture contract with both teammates. Tawassul can start the shared Phase 5 Chromium runner from this contract while Phases 3 and 4 progress. Include the runner and fixtures in the fork's shared base before teammates start their Playwright specs. [Shared Playwright runner](05-playwright-use-cases.md#prepare-the-shared-runner)
