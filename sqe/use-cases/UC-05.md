# UC-05 — Settle an order through exceptional manual payments

| Field | Value |
|---|---|
| Workflow | W1 Record a manual payment |
| Author | Member 3 |
| Primary actor | Orders Manager (team permission `event.orders:read` + `event.orders:write`) |
| Goal | Record money received for an order when it does not arrive as one exact payment, without creating duplicate or wrong payment records |
| Trigger | The organiser's bank statement shows a transfer for an order |
| Requirements | PAY-01, PAY-02, PAY-03 (see `Documents/Phases/01-windows-setup.md`) |
| Business rules | BR-01 payment eligibility and status |
| Risks | R1 duplicate payment, R2 status without matching records, R5 wrong amounts, R15 negative amount accepted |
| Automation | `src/tests/team/e2e/uc05-uc06.spec.js` (tests titled `UC-05 …`) |

## Preconditions
1. The SQE instance is reset (`sqe\windows.ps1 reset`) and the manager is logged in to the control panel.
2. The event `sqe-orders/orders` sells a EUR 20.00 ticket; the order has one active ticket position.
3. The order is in the state named in each flow (fixture alias in brackets).
4. Customer e-mail notification is switched off in the form (no real e-mail).

## Main flow — partial payment, then the remaining amount (`m3_partial`, pending)
1. Manager opens the order detail page.
2. Manager selects **Mark as paid**.
3. System shows the payment form prefilled with the outstanding amount (20.00).
4. Manager enters **12.00**, unticks *Notify customer by email*, selects **Create payment**.
5. System confirms "The payment has been created successfully." and the order remains **Pending**.
6. Manager selects **Mark as paid** again.
7. System prefills the remaining **8.00**.
8. Manager selects **Create payment**.
9. System confirms the payment and shows the order as **Paid**.

## Alternative flows
- **A1 — Reuse a matching unconfirmed payment (`m3_reuse`)**. Precondition: the order already has an unconfirmed (*created*) manual payment of 20.00. At step 4 the manager enters 20.00. The system confirms the *existing* payment instead of creating a second one; the order becomes Paid.
- **A2 — Overpayment (`m3_overpay`)**. At step 4 the manager enters 25.00. The system confirms the payment and marks the order Paid; the order total stays 20.00 (the 5.00 surplus is visible as an overpayment for a later refund decision, which is out of scope).

## Exception flows
- **E1 — Invalid payment date (`m3_bad_date`)**. At step 4 the manager enters the date `2026-13-45`. The system must not record a payment. *Expected by usability heuristics and by the cancel form's behaviour:* the form is shown again with an error on the date field. *Observed baseline:* the system redirects to the order detail without an error message (known defect H5, same root cause as UC-01 E1). Automated as two tests: `exc 1` (state unchanged — passes) and `exc 1b [known defect]` (inline error — marked `test.fail()` until fixed).
- **E2 — Order already canceled (`m3_canceled`)**. The order detail does not offer **Mark as paid**; requesting the payment form directly (`…/transition?status=p`) returns HTTP 405. Nothing changes.
- **Probe H2 — Negative amount (`m3_neg_amount`)**. Boundary just below a valid positive amount. Expected by the business rule: rejected, no payment. (Not counted as a UC flow; it is a boundary probe for hypothesis H2.)

## Postconditions (asserted through `GET /api/v1/.../orders/{code}/` before and after)
| Flow | Status | Confirmed payments | Other |
|---|---|---|---|
| Main | `n` after the first payment, `p` after the second | 2 payments, sum 20.00 | total 20.00, positions unchanged |
| A1 | `p` | 1 payment — **same id** as the seeded one | no extra payment record |
| A2 | `p` | 1 payment of 25.00 | total 20.00, positions unchanged |
| E1 | `n` | 0 | whole order identical to before |
| E2 | `c` | 0 | whole order identical to before |

## Test design techniques
- Equivalence partitions of the amount: partial (< outstanding), exact, over (> outstanding), negative (invalid).
- State transitions: `n → n` (partial), `n → p`, `c → c` (disallowed payment).
- Repeated-request / duplicate check: A1 asserts the payment count stays 1.
